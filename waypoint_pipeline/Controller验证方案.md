# Controller 验证方案

> 目的：在**参考线完全不变、车辆不人为偏离**的前提下，验证「参考线 → 时间 waypoints → 控制器 → (steer, throttle)」这条链路在 10 Hz 下的时序正确性与跟随性能。
> 本文是**要求文档**（写码前定稿），不含实现代码。

## 1. 核心时序要求（硬性，不可妥协）

| 项 | 要求 | 依据 |
|---|---|---|
| 控制器调用频率 | **10 Hz**，每个控制 tick 调一次 `GeometricController.compute(wp_ego, speed_kmh, dt=0.1)` | 与 `config.SIM_DT=0.1` 一致 |
| waypoints 时域/频率 | 未来 **3 s @ 2 Hz = 6 点**，时刻为 `t+0.5, t+1.0, …, t+3.0` | `config.WP_HORIZON_S/WP_FREQ_HZ` |
| 窗口形态 | **随当前时刻连续滑动**：`τ_k = t + 0.5k`，绝不吸附到 0.5 网格 | 见 §1.1 |
| 生成时机 | **每个 tick 都重新生成**，禁止复用/缓存上一 tick 的数组 | — |
| 坐标系 | 当前车辆**真实 ego 系**（x 前、y 左，米），用本 tick 的 `v.position / v.heading_theta` 转换 | 与数据集约定一致 |
| 输出 | `[steering, throttle_brake]`，直接 `env.step(action)` | `controllers.compute` 返回约定 |

### 1.1 采样时刻定义（唯一权威）

第 t 秒这次调用，控制器收到的 6 个 waypoints 对应的**绝对时刻**为：

```
τ_k(t) = t + 0.5 · k        k = 1, 2, …, 6         （共 6 点，不含 t 本身）
```

两条推论，都必须成立：

1. t 每前进 **0.1 s**，**全部 6 个 τ 同步前进 0.1 s**（窗口整体连续滑动，不是重新对齐到某个网格）；
2. 相邻 τ 之差恒为 **0.5 s**（= 2 Hz），与 t 的相位无关。

逐 tick 展开（`…` 处按 0.5 递增，无跳跃）：

| 调用时刻 t | τ₁ | τ₂ | τ₃ | … | τ₆ | 相位 = t mod 0.5 |
|---|---|---|---|---|---|---|
| 0.0 | 0.5 | 1.0 | 1.5 | … | 3.0 | 0.0 |
| 0.1 | **0.6** | **1.1** | **1.6** | … | **3.1** | 0.1 |
| 0.2 | 0.7 | 1.2 | 1.7 | … | 3.2 | 0.2 |
| 0.3 | 0.8 | 1.3 | 1.8 | … | 3.3 | 0.3 |
| 0.4 | 0.9 | 1.4 | 1.9 | … | 3.4 | 0.4 |
| 0.5 | 1.0 | 1.5 | 2.0 | … | 3.5 | 0.0（相位循环，周期 = 5 个 tick） |
| 0.6 | 1.1 | 1.6 | 2.1 | … | 3.6 | 0.1 |

**读法示例**：t = 0.1 s 这次调用，给的是 **0.6, 1.1, 1.6, 2.1, 2.6, 3.1** 这 6 个时刻的路径点，输出 0.1 s 对应的 steer/throttle。

### 1.2 禁止的实现写法（反例，逐条对应要抓的 bug）

| 错误写法 | 实际后果 | 被哪条断言抓 |
|---|---|---|
| 把 t 对齐网格：`round(t/0.5)*0.5`、`floor(t/WP_DT)*WP_DT`、`searchsorted` 取最近数据集帧 | t=0.1 时仍输出 0.5…3.0，等于给了最多 **0.4 s 前的旧窗口**；表现为前瞻点周期性抖动，而**整圈平均误差几乎不变**，事后极难归因 | T1 |
| 复用上一 tick 数组、只把索引往前挪一格 | 首点距离变成 v·0.1 而非 v·0.5，时域被压缩 | T1 |
| 把 t 本身（原点）算进 6 点里 → 7 点 | `controllers.path_from_waypoints()` 已 `np.vstack([np.zeros(2), wp])` 补原点，重复原点后累计弧长与前瞻取点整体错位 | T2 |
| 用固定间距（如恒 9.7 m）代替 v·0.5 s | 车速变化时（弯道限速）输入与真实行驶能力脱钩 | T2 |

### 1.3 本方案用弧长表达同一件事

```
s_k = s_car + v · 0.5 · k        k = 1, …, 6
```

只要 ① `s_car` 是**连续投影**（段内插值，不是 2 m 重采样的量化索引）、② `v` 是**当前实测车速**，滑动相位就自动成立，**不需要任何取整或对齐**。§5 的 T1/T3 即对它的逐 tick 校验。

## 2. waypoints 怎么生成（参考线，不偏移）

| 步骤 | 做法 |
|---|---|
| ① 参考线 | `tu.extract_lap_reference(output/trajectory_expert.json)` → 单圈闭环路径，按 2 m 重采样得 `px, py`（含法向 `nx, ny`） |
| ② 投影 | 把车辆**当前世界位置**投影到参考线，得到连续里程 `s_car`（米）与切向 `θ_ref`。**必须段内插值**，不得直接用重采样点索引（2 m 量化会让 waypoints 每 tick 跳 2 m，控制器跟着抖） |
| ③ 未来点 | `s_k = s_car + v · (0.5·k)`，k=1…6，`v` = 当前车速 m/s；`s > L` 时按 `mod L` 闭环回绕（参考线是闭环，不需要末端外推） |
| ④ 世界坐标 | `point_at_s(s_k)` 在重采样折线上线性插值 |
| ⑤ 转 ego | `make_waypoints.world_to_ego(pts, 当前位置, 当前航向)` → `[WP_COUNT,2]`（当前 6 点） |

伪码（写码时照此实现，不新增底层依赖）：

```
v      = agent.speed_km_h / 3.6
s_car  = ref.project(agent.position[:2])          # 连续里程, 段内插值
s_k    = (s_car + v * 0.5 * arange(1, 7)) % L     # 闭环回绕 (6 点)
wp_world = ref.point_at(s_k)
wp_ego   = world_to_ego(wp_world, agent.position[:2], agent.heading_theta)
action   = ctrl.compute(wp_ego, v*3.6, dt=0.1)
```

### 2.1 为什么用「当前速度沿参考线推进」，而不是回放专家时间轴

| 来源 | 含义 | 本验证是否采用 |
|---|---|---|
| **参考线 + 当前速度**（本方案） | "完美路径预测器"：路是给定的，未来点由**车自己的速度**决定。车快则点密/疏自洽，与控制器纵向输出闭环自洽 | ✓ |
| 专家 `wp_world` 按 sim_t 索引（`evaluate.WaypointReplay`） | 隐含"车必须按专家时刻表行驶"，一旦实际速度与专家不同，输入与真实几何脱钩；且相位吸附到数据集 0.1 s 帧 | ✗（仅作对照） |

两者在"车贴着参考线跑"时结果接近，但只有前者能作为将来接真实预测模型的**接口模板**（模型输出的也是"沿路几何点"）。

### 4.1 叠加层（`SceneOverlay`，只用于观察，不参与任何判据）

| 元素 | 画法 | 为什么这么画 |
|---|---|---|
| 6 个 waypoints | 6 个**离散小球**，直径 0.55 m，颜色由近到远变暗（亮绿→暗绿） | 它们是 2 Hz 的 6 个**采样点**，不是路径；连成折线会被误读成“规划线”。亮度梯度让人能直接读出点序与时间远近 |
| Pure Pursuit 前视点 | 1 个更大的黄球，直径 0.95 m | 它是控制器“在看哪”的答案。直道上黄球（8.86 m）落在车头与第 1 个点（`v·0.5` = 9.72 m）之间，这本身就是 §1.1 时序的现场证据 |
| steer / throttle | 屏幕左侧两个示波器，**过去 10 s 滚动曲线**（steer 青，满量程 ±0.6 rad；throttle 正绿负红，±1） | 放在左侧是为了避开 MetaDrive 自带的 HUD 文本框（它在中右区域，重叠过） |

两个实现坑（都是截图实测发现的，不是推演）：

- **3D 线用 `LineSegs` 顶点色会被场景光照压成黑色**，必须挂 Material。官方 `make_point_drawer` 内部就是挂 Material 的，改用后颜色正确，且它自带 `reset()` 点回收池，适合每 tick 刷一组点。
- **点尺寸换算**：`sphere.egg` 是半径 1 的单位球，`make_point_drawer(scale=S)` 内部只做 `S/10`，所以**世界直径 = S/5 米**。直接给 `scale=22` 会得到直径 4.4 m 的球（比车道还宽）。代码里因此按“想要的直径米数”写常量。

## 5. 判据（全部满足才 PASS）

### 5.1 时序正确性（本方案新增，优先级最高）

| # | 断言 | 阈值 | 整圈实测 | 抓的是什么 bug |
|---|---|---|---|---|
| T1 | 首点（τ₁ = t+0.5）到车的**弦长** \`\|wp_ego[0]\|\` = `v·0.5 s` | 逐 tick 最大相对误差 ≤ 5% | **0.0010** | 窗口吸附到 0.5 网格 / 忘了随 t 滑动（§1.1、§1.2） |
| T2 | 6 个 waypoint 的相邻间距 = `v·0.5 s` | 中位相对误差 ≤ 5% | **8e-06** | 采样频率写错、用了固定间距 |
| T3 | `s_car` 每 tick 增量 = `v·0.1 s` | 最大相对误差 ≤ 10%，且单调不回退 | **0.0016**（最小步长 1.939 m） | 投影量化跳变、闭环回绕出错 |
| T4a | `wp_ego` 用**独立写出的** `ego_to_world` 反映射后 vs 生成时的 `wp_world` | max ≤ 1e-6 m | **0.0** | `world_to_ego` 公式笔误（逆函数独立写出，符号写反则不行） |
| T4b | 车在 τ_k 时刻的**实际位置** vs 当时发出的 `wp_world[k]` 的横向偏差 | max ≤ 0.3 m | **0.097 m** | 端到端语义：整条链路（ego 系/航向/前瞻）约定写反则爆表 |
| T5 | 首点 x > 0；且首点横向位置与参考线局部曲率一致：`y ≈ ½κd²` | min x > 0；残差 ≤ 0.15 m | **9.67 m** / **0.114 m** | 航向/左右轴约定写反 |

两条实现注记：

- **T5 不是 "y≈0"**：弯道上路径本身会弯，首点横向预期值为 `½κd²`（R=60 m、d=9.7 m 时达 0.79 m）。原阈值 0.2 m 会在每个弯道误报，已改为曲率一致性残差（实测最大 0.114 m，发生在最急的弯）。
- **时序断言排除前 5 个 tick**：`env.reset` 后第一帧车速读数已达 70 km/h 但实际只走 1.56 m（物理瞬态），计入会让 T3 误报 20%。与 waypoints 生成无关。
- **T1 用弦长而非弧长**：弯道上弦比弧短（实测最多差 0.4%，9.68 vs 9.72 m），5% 阈值充分包含此几何差。

### 5.2 跟随性能

| 指标 | 阈值 | 整圈实测 |
|---|---|---|
| 完圈 | True | **True**（5550 tick / 554.9 s） |
| mean \|横向误差\| | ≤ 0.05 m | **0.0179 m** |
| p95 / max \|横向误差\| | ≤ 0.10 / ≤ 0.25 m | **0.0848 / 0.1132 m** |
| 碰撞帧 | 0 | **0** |

## 6. 已定决策与明确不做

### 6.1 已确认（写码不得再改）

| # | 决策 | 结论 |
|---|---|---|
| D1 | 窗口点数 | **6 点（3 s @ 2 Hz）**，不含 t 本身（原点由控制器内部补）。时域由 5 s 缩到 3 s：更远的点对控制无用，弯道上转角更大、拟合 loss 更高，反而会把模型带偏 |
| D2 | 采样时刻形态 | **连续滑动**，t=0.1 时就是 0.6, 1.1, …, 3.1；禁止对齐到 0.5 网格 |
| D3 | waypoints 来源 | **参考线几何 + 当前实测速度沿弧长推进**（§2），不用专家时间轴回放 |
| D4 | 控制频率 | **10 Hz**（`dt=0.1`，与 `SIM_DT` 一致） |
| D5 | 出界判据口径 | 沿用 `run_pipeline.py`：max(1%, 专家同窗基线+0.5%)，不另建口径 |
| D6 | 时序断言窗口 | 排除前 5 个 tick（reset 后物理瞬态，与 waypoints 生成无关） |

### 6.2 明确不做

| 项 | 说明 |
|---|---|
| ~~横向 ±1 m 随机偏移~~ | **已取消**：不制造偏离，车从起点自然沿参考线行驶 |
| ~~车辆传送、纠偏收敛判据、倒计时多轮~~ | **已取消**（与偏移场景绑定）。若之后要"多场景轮演 + 屏显倒计时"，另开一节讨论，本期不做 |
| ~~控制频率 5 Hz~~ | 已改为 10 Hz（见 D4） |
| 本验证不覆盖的部分 | 感知/预测质量。输入是完美参考线，所以 PASS 只证明"控制器+接口"没问题；将来模型给的 waypoints 有偏、有噪、有点距不均，需另做鲁棒性验证 |
| `offroad` 判据口径 | 取 `env._is_out_of_road()`，在车道段接缝处会瞬时判真；max 横向 0.14 m ≪ 车道宽 3.5 m，车不可能真冲出路外。故本方案把它列为 ≤1% 的软指标，异常放大才查 |
